1. Executive summary

MyHealth Care is a cross-platform Flutter application that unifies a patient's medical history, runs an AI-driven appointment scheduler that predicts no-shows, and gives clinical staff a rules- and AI-prioritised task workflow. It is offline-first: all data lives in a local SQLite database, the app is fully functional with no network and no API key, and the AI layer degrades gracefully to a deterministic mock when the cloud model is unavailable.

2. Research questions & how each is answered

The project proposal defines three problems, each a research question with a matching objective. The codebase maps 1:1 onto them.

RQ1 — Scattered records → a unified, timeline-based health profile

  • Merged health timeline — medical records (visit notes, labs, imaging, prescriptions, vaccinations, discharge, referrals) and vitals measurements are merged into one reverse-chronological feed, grouped by month, with type filters and free-text search.
  • AI health summary — an AiService produces a narrative summary plus key events, trends, and red flags from a strict JSON contract. Key events appear as inline markers on the timeline; trends deep-link to the matching vitals chart.
  • Record detail — lab panels render as a table with each value flagged against its reference range (normal / low / high / critical), never colour alone.
  • Every AI surface carries a permanent "informational only, not medical advice" banner.

RQ2 — Manual booking & wasted capacity → an AI-driven scheduler

  • No-show prediction model — a class-balanced logistic regression trained offline in Python on a synthetic 8,500-appointment dataset, exported to JSON, and run as pure-Dart inference on device. 11 features (lead time, prior no-show rate, first-visit, chronic condition, visit type, day/hour, reminders acknowledged, …).
  • Python ↔ Dart parity — a test asserts the on-device prediction matches the Python model within 1×10-6 on every frozen case, so the reported accuracy numbers are the numbers the app actually uses.
  • Booking wizard — department → doctor → day, then every open slot is scored and ranked lowest-risk-first, each with a plain-language reason.
  • Explainability — per-feature contribution breakdown for any prediction.
  • Risk-adaptive reminders — the reminder schedule escalates with the predicted risk band (1 reminder for low risk, up to 3 with a confirm-or-release request for high risk); idempotent across reschedules.
  • The predicted risk and band are stored on the appointment for later analytics.

RQ3 — Staff buried in paperwork → task prioritisation & early risk identification

  • Deterministic rule engine (runs with AI switched off, no network): severe blood pressure / low SpO₂ / high glucose, critical lab values in the last four months, medication gaps for known chronic conditions, and overdue follow-ups. Each finding gets a severity and a stable de-duplication key.
  • Task generator — turns open risk flags into rule-scored staff tasks (urgent 0.9 / warning 0.6 / info 0.3) with a due date, idempotent on re-run.
  • AI prioritisation — an AI score is layered on top and blended with the rule score at read time (weight configurable in settings); the board is fully useful with AI off.
  • Task board — every task shows its rule score, AI score, due date and a one-line rationale.
Architectural note (stated for the defense): local-only storage means "a doctor opens a patient's chart" happens within one device's database, not across a network. This is handled by a repository layer that all features talk to — a future networked backend is a one-class swap, not a rewrite — and is framed in the report as offline-first architecture, with multi-device sync listed under Future Work.

Structure

Feature-first (lib/features/<feature>/{presentation,application}) over a three-layer core: domain (entities + repository interfaces — the swap point) → data (Drift database, repository implementations, synthetic seeder) → services (AI, ML, notifications, rules).

Synthetic data

A deterministic seeder builds 5 departments, 12 doctors with weekly schedule templates, 60 patients aged 8–83 with ~2 years of history (records, labs with real reference ranges, vitals, medications, appointments). A hidden per-patient no-show tendency is embedded so the ML model has a real signal to learn. No real patient data — reproducible, no ethics exposure.

  • Every fallible operation returns Result; failures surface as retryable messages, never crashes.

5. Results & evidence

5.1 No-show model (RQ2)

Class-balanced logistic regression, no-show-v1. Test set 2,145 appointments, 25.1 % no-show rate.

ModelAccuracyPrecisionRecallF1ROC-AUC

The model beats both baselines on ROC-AUC and recall — it catches ~62 % of real no-shows, which is the metric that matters for filling wasted slots. Strongest predictors: prior no-show rate (+1.02), lead time (+0.35), first visit (+0.28).
