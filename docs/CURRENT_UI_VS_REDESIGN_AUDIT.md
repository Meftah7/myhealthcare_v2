# Current app vs. approved redesign: coverage audit and plan

Baseline record: this comparison was prepared before the subsequent upgrade. The local design now has 141 frames; see the [implementation and verification status](figma-redesign/IMPLEMENTATION.md) for changes made and remaining runtime checks.

Prepared 3 October 2026. This is a planning review; it does not change Flutter UI or the Figma file.

## What was compared

- Current Flutter routes, shared widgets, role workspaces, feature screens and their visible actions in `lib/app/` and `lib/features/`.
- The approved, offline 78-frame design in `docs/figma-redesign/design.js` and `preview.html`, plus its `implementation-map.json`.
- A separate [finding for each of the 78 frames](figma-redesign/FRAME_BY_FRAME_AUDIT.md), including routes, sheets and states the design does not yet show.
- Existing integration notes and the earlier `docs/UI_UX_REDESIGN_PLAN.md`.

The offline design has 9 Auth, 31 Patient, 16 Staff and 22 Admin frames. The editable Figma file currently contains 56 of those frames; its 22 Admin frames and prototype links remain pending, as recorded in the redesign README. The app has 64 `GoRoute` declarations. The 78-frame mapping points to 45 distinct presentation files because many frames are steps or states of one route. A mapping is evidence of a corresponding app surface, **not** proof that every control or state appears in the design. Flutter is unavailable in this session and there is no current-app screenshot set in the checkout, so current visual/layout findings below come from widget source. The preview images were inspected; live visual differences still need measurement.

## What the approved design gets right

The pale blue headers, blue primary actions, white cards, shorter lists and clear task priority are useful across all roles. Current Flutter already adopts much of that shared styling and has working routing, state management, data and permissions behind the screens. Keep the five role destinations, real Bahrain dinar amounts, English/Arabic support, dark and high-contrast themes, and the existing clinical and family-access rules. Improve each real task path around the shared visual direction.

## Delivery sequence

1. **Freeze coverage before polishing.** Use this matrix against the 64 routes and their sheets. Capture the current app on a machine with Flutter at 320, 390, 840 and 1440dp; include Arabic, dark mode and large text. Record existing behavior beside each screenshot. No runtime screenshot claim can be made from this checkout today.
2. **Close the P0 design gaps.** Update the combined design specification and preview with photo management, real Preferences controls, the correct password-change path, family permissions, booking exceptions, clinical state variants and missing admin actions. Finish the editable Admin section and prototype links in the same Figma file when the connection permits. Preserve the approved color/spacing direction. Review the new frames before propagating UI changes.
3. **Update shared Flutter components.** Apply responsive header/action rules, input/read-only states, grouped navigation, busy/error feedback and consistent sheets once in shared widgets. Reuse role-aware variants instead of duplicating styles.
4. **Complete role journeys.** Implement and visually review Patient Profile → photo/preferences/family, booking → ticket → billing, Staff queue → chart → consultation/result, and Admin attention → assignment/billing/users. Then cover P1 routes and overlays from the table.
5. **Verify preservation and polish.** Run `flutter analyze`, targeted and full Flutter tests, web builds and route/deep-link checks with the pinned toolchain. Compare real screenshots with the approved preview at the listed widths and themes; inspect keyboard, screen reader, permission, loading/empty/error and mutation-failure states. Mark a package complete only when its old actions remain reachable and its new visual states are reviewed.

The existing `docs/figma-redesign/IMPLEMENTATION.md` records prior integration checks. It is a mapping of the first design pass; this audit records fidelity and feature gaps to close in the next pass.
